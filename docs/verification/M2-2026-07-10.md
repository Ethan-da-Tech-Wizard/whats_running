# M2 verification and closure

Status: Accepted historical record  
Date: 2026-07-10  
Reference: Arch Linux x86_64, kernel 7.1.3-arch1-1, Hyprland/Wayland, 16 logical CPUs, approximately 15.2 GiB RAM, Rust 1.96.0

## Delivered requirements

- CPU percentage from process tick delta versus aggregate tick delta, scaled so 100% is approximately one logical CPU.
- Storage read/write bytes per second from monotonic counters and sample wall time.
- Stable identity `(PID, start_ticks)` prevents PID reuse from joining unrelated histories.
- Starts/exits are explicitly “observed between samples,” not guaranteed event capture.
- Memory and swap context comes from procfs.
- History/output is hard-capped at 120 samples and remains in memory only.
- JSON schema v2 emits a single valid history document.

## Verification commands and results

```text
cargo fmt --check
cargo test --release -- --nocapture
cargo clippy -- -D warnings
cargo build --release
whats-running --samples 100 --interval-ms 1
whats-running --json --samples 3 --interval-ms 10
python -m json.tool /tmp/wr-history.json
```

- Seven release-mode tests passed.
- Clippy passed with warnings denied.
- Synthetic procfs fixture enumerated 2,000 process directories and met the 250 ms collector assertion. The entire test suite, including fixture construction/removal, completed in approximately 0.06 seconds on the reference environment.
- A 100-sample live constrained-environment run measured collection mean 0.425 ms, minimum 0.212 ms, and maximum 0.715 ms. Rendering and requested sleep are excluded from those collection timings.
- Three-sample schema-v2 JSON parsed successfully and every sample contained exactly one observer record.
- `--samples 121` failed explicitly with the documented bound.

## Budget disposition

- SR-013 (under 250 ms at 2,000 processes): verified against a synthetic fixture on the reference host.
- SR-010 (one-second default interval): verified in CLI defaults; lower intervals are allowed for controlled testing, with the hard history bound limiting duration rather than CPU. A future interactive mode should add a safer refresh floor.
- SR-011 (below 1% of one core at 500 processes): not directly proven by the synthetic functional fixture because it does not run sustained sampling against live kernel tasks. The much stronger per-collection latency evidence suggests ample headroom, but this is explicitly an inference.
- SR-012 (below 100 MiB at 2,000 records across default history): the original wording is ambiguous and unrealistic if interpreted as 2,000 × 120 fully cloned string-rich samples. M2 uses a hard bound, but exact memory profiling is deferred until M3 chooses its retained view/model. The requirement requires revision by ADR before M3 closure.

## Known limitations retained

- Sampling can miss processes that start and exit between reads.
- Wall-clock milliseconds are used for I/O rate intervals; CPU uses kernel aggregate ticks.
- Exact numeric failure reasons are not yet preserved per field in JSON.
- “Complete” visibility remains relative to procfs namespace, permissions, and sampling boundary.
- History is exported at program completion, not streamed or persisted.

M2 is complete against its milestone exit criteria. These limitations are future work, not concealed failures of the stated M2 contract.
